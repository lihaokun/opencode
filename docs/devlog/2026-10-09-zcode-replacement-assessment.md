## 做了什么

回答"是否用 ZCode 全面替换 opencode fork"的评估轮，未改产品代码：

1. **盘点 fork 自身工作**：15 个 closed issues + 19 个 merged PRs，作为对照基准。
2. **ZCode 身世与治理核查**：独立代码库（pnpm/独立包结构，无 opencode 血缘）；投放式厂商仓库（issue 跟踪关闭、无 CONTRIBUTING、唯一 release v3.14.3、NOTICE 明示源码不承诺全部官方功能）；Z.ai 官方 GLM 系 harness。
3. **三路专项源码对照**（浅克隆逐项核查）：流处理健壮性、会话循环健壮性、工具/子代理/MCP/压缩能力。结论：fork 修复的问题约 3/4 在 ZCode 不存在（多数有更强实现，含 issue #46 三个 P0）；ZCode 存在同型缺陷两处半（有界周期 doom-loop、content_filter 分类缺失、发送前预检部分存在）。
4. **替换分析**：治理面（贡献者→私改者）为主要成本；三条路线（替换/参照实现/并行），倾向 B（维持 fork + ZCode 作参照实现）+ 可选 C（GLM 日常工具并行）。

## 关键决策与理由

- **先查治理面再查代码面**：issue 跟踪关闭 + 投放式发布直接决定"我们与代码库的关系"，比任何单点功能对比都更影响替换决策。
- **问题级对照以 fork 的 closed/merged 清单为基准**，而不是泛泛比较功能表——这样每个结论都可回溯到"我们修过什么、对方有没有同款问题"。
- **诚实列出 A 路线（全面替换）的成立条件**（§5.5），避免立场先行；当前四条均不成立。

## 经验教训

- **对照/选型先评估治理面**：issue 跟踪是否开放、发布是投放还是演进、有无可 rebase 的历史，决定我们能以什么身份使用代码（贡献者还是私改者）；这一判断比功能对照更早地约束结论空间。
- **血缘判定看代码不看出处**：GitHub `fork: false` 不代表无血缘，但包管理器、目录结构、存储路径、依赖清单可以；本项目两个判断（opencode 双 runtime、ZCode 独立库）都靠"生产可达链/结构证据"而非元数据。
- **替换类评估要同时盘"对方有我没有"和"我有对方没有"**：单向差距表会得出"全面升级"的错觉；双向资产表才能暴露"资产互换 + 无法回馈"的真实结构。
