# 用摘要上的 n 恢复近期原文

状态：2026-11-20 确认实施。

## 已确认的读写语义

- 时刻 `i` 由发起本次压缩的既有 marker 定位。摘要请求只处理该标记之前的历史。若压缩期间收到新消息，这些消息排在保留原文之后，且不计入 `n`。
- 成功的摘要 assistant 记录携带可选非负整数 `n`，单位为消息条数。其值取最终成功那次尝试实际保留的原消息数。一次写入必须同时表达摘要成功和对应的 `n`，从而消除成功已可见、保留边界尚未生效的窗口。
- 组装模型历史时，从已落盘的标记前历史取最后 `n` 条保留原消息，按原顺序放在摘要之后，随后接上标记后的新消息。保留原文沿用原消息 ID，不重新插入。失败、未完成的摘要不结算 marker。

例：标记前有 16 条原消息。若最后成功的请求总结前 13 条，摘要记录 `n = 3`。第 14～16 条沿用数据库里的原记录；压缩期间收到的 worker 汇报接在第 16 条之后。

## 旧会话的内存升级

在加载会话历史、能同时看到摘要、marker 和相关历史时统一补齐 `n`：

1. 摘要已有 `n` 时直接使用，显式的 `0` 也优先。
2. 摘要缺少 `n`、旧 marker 有 `tail_start_id` 时，按旧读取规则确定保留区段，将对应的消息条数填入内存中的 `n`。
3. 两者都没有时使用 `0`。旧版本若在成功与写边界之间崩溃，沿用原来读取时的零保留语义。

不回写旧库，不做批量迁移。重新打开旧会话可以再次换算；运行循环只消费读取层归一化后的结果。

## 自动压缩与续行

正常请求完成后触发 usage 压缩时，根据实际选区记录 n。发送前预检或 provider 拒绝时，以那次请求的原用户 U1 为锚，U1 及其后已落盘的原消息均为必保；marker 之后到达的输入按序独立保留。沿用合成继续消息唤醒下一步，不再复制 U1。继续消息的配置取最新实际输入。溢出恢复中已有的媒体降级只作用在模型视图，原始文件 part 保留。

必保区独立计费；额外旧历史仍按 5% 档位和 25% 上限、配置上限选择，并受主模型剩余可用输入限制。必保输入本身放不下时终止；摘要后完整工作请求还需容纳系统、工具、摘要和晚到输入。旧库读取转换不推测缺失的旧边界。

## 验证

基准 2c949c560c。最小反例是在摘要 step-finish 已写入、处理函数未返回时重新从 DB 投影。另覆盖新旧混合和失败摘要、连续压缩、显式零、晚到 U2、不复制 U1、工具结果不重做、保留区超过 25% 仍能恢复，以及不可缩小的必保部分。契约涉及 V1 消息 schema、SDK、运行循环、历史读取和 restoration；不增加数据库迁移。

### 实现和兼容

预检与 provider 拒绝入口将触发该请求的用户 ID 写进待处理 marker 的 `protected_from`。按原请求准备后的系统提示、工具定义估算的 `fixed_input_tokens` 只用于对应输入的预算；出现不同的真实输入时不以过期估值拒绝恢复。重新发送前对完整的新请求再做预算判断。合成继续消息只承载控制指令和应沿用的执行配置；若它自身又遭拒绝，继续使用所关联的原始用户 ID。fork 时同步映射这些 ID。

历史加载在跨页的完整消息流上解释最新已结算的 marker。原消息不含旧 marker 和摘要尝试。旧指针即使落在隐藏的失败摘要上也按该行定位，找不到指针时沿用原来的扫描范围；成功摘要在内存补齐 n。已有请求因媒体过大降级后，后续摘要若继续保留同一原消息，模型视图延续占位表示，SQLite 中的附件不变。

### 实测结果

修前：摘要只接收前 13 条，首次成功已落库时另读 DB，保留原文为 0/3。修后同一时点得到 n=3 和原来的 3 个 ID，晚到输入在其后。旧 anchor 跨 3 页以及跨旧控制消息的换算均通过；重复读取不改 SQLite。独立复核发现并验证修正了跨代旧摘要回退、媒体重新进入请求、usage 续行丢配置和连续压缩丢待办输入。连续未回答的多个用户和拒绝前后到达的消息均以原 ID 保留。工作区使用脚本化本地 provider 验证，未替换 ker79 上的安装。
